# Reconciling the PM4 crash record (2026-10-19, arm C)

The parent's question: the doc's table says the old path ran 8 times with 0 asserts, `docs/pm4-repro/before.txt`
says 8 runs with `asserts=1`, and the doc says the warm-route session saw the assertion in 4 of 17 runs.
Those three cannot all be the same thing. They are not: only one of the three is a crash record.

## 1. What the counters actually count

`tools/macos/pm4_repro.sh:59-63` (identical in every worktree on this machine, and in the only commit that
ever touched the file, `de65de0`):

```
bad=$(grep -c 'Bad PM4 packet' "$dir/$tag.log" 2>/dev/null || true)
stop=$(grep -c 'assert_fail\|GPU library assertion failed\|Unreachable code' "$dir/$tag.log" 2>/dev/null || true)
changed=$(grep -c '^Submit check: submission' "$dir/$tag.log" 2>/dev/null || true)
line="... bad_pm4=${bad:-0} asserts=${stop:-0} changed_submissions=${changed:-0} created=${compiles:-?}"
```

- `bad_pm4` counts **lines containing `Bad PM4 packet`** - the first line of the historical crash only.
- `asserts` counts **lines matching `assert_fail`, `GPU library assertion failed` or `Unreachable code`** -
  i.e. the crash *chain*, not the crash *cause*. A run that dies with `Unreachable code!` but never printed
  `Bad PM4 packet` scores `asserts=1 bad_pm4=0`.
- `changed_submissions` greps `^Submit check: submission`, which no build ever prints: the real lines are
  `Submit check: N of M graphics submissions changed ...` and `Submit check: submission N's dcb ...`. It is 0
  in every summary ever written, for every run, including ones with a live hash check. It measures nothing.
- `created=` is the last column; it was added with the committed script.

So `asserts=1 bad_pm4=0` is *possible* in principle (a different GPU assertion). The question is whether it
ever happened in the `before` series. It did not.

## 2. The `before` series is 8 clean runs, and `before.txt`'s `asserts=1` is an artifact

Three independent checks, all on the retained files:

**(a) The count does not reproduce from the file it labels.** For every tag in `before.txt`, the retained
`out/pm4_repro/before/<tag>.log` has zero lines matching the assert pattern and zero matching `Bad PM4 packet`:

```
attack-1  max_draws=902  log max=902  assert_lines=0 bad_pm4=0
combat-1  max_draws=894  log max=894  assert_lines=0 bad_pm4=0
interact-1 max_draws=812 log max=812  assert_lines=0 bad_pm4=0
street-1  max_draws=907  log max=907  assert_lines=0 bad_pm4=0
attack-2  max_draws=719  log max=719  assert_lines=0 bad_pm4=0
combat-2  max_draws=732  log max=732  assert_lines=0 bad_pm4=0
interact-2 max_draws=777  log max=777  assert_lines=0 bad_pm4=0
street-2  max_draws=931  log max=931  assert_lines=0 bad_pm4=0
```

`max_draws` matches `before.txt` **exactly for all eight tags**, so `before.txt` describes precisely these
files - and these files contain no assertion. Every one of them ends:

```
out/pm4_repro/before/attack-1.log:
Warm run: 0 pipelines created this run, 493 preloaded from the cache; compiles still running at the time limit - asking the game to quit
GPU process exited (0)
```

`GPU process exited (0)` in all eight. A bb-gpu assertion ends the process non-zero with `STOP: GPU library
assertion failed` in `bb-probe`'s output; there is no `STOP:` line in any of the eight logs.

**(b) The same session's own table says 0.** `docs/PM4_TORN_SUBMISSIONS.md:82` (written by the same session,
3 hours later):
`| before (old async path) | BB_SUBMIT_ASYNC=1 | 8 (attack, combat, interact, street x2) | 0 | 0 of ~5M |`.
The log lines agree with the table, not with `before.txt`.

**(c) `before.txt` was not written by any script on this machine.** Its lines have no `created=` column:
`before attack-1 max_draws=902 bad_pm4=0 asserts=1 changed_submissions=0`. Every copy of `pm4_repro.sh` in
every worktree (and its only committed version) emits `created=${compiles:-?}`, and `after.txt`,
`before-cold.txt` and `delay-async.txt` all carry it. `out/pm4_repro/before/` also has **no `summary.txt`**,
while `after/` and `before-cold/` do. So `before.txt` came from an earlier, uncommitted loop whose assert
counter is not on disk; whatever that counter read, it was not a line in these logs. The `1` is a counter
artifact, not an assertion, and it cannot be reconstructed further from what survives.

**Conclusion for the parent's "six of six":** the series is 8 runs, not 6, and it is 0 of 8, not 8 of 8. It is
the *same* eight runs the doc's table scores 0 - this record does not disagree with itself once `before.txt`
is set aside.

## 3. Which build each series ran (the part that does matter)

The `before` series did **not** run pre-fix code. It ran the *fixed* build with the async env switch:

```
out/pm4_repro/before/attack-1.log:
GPU process: graphics submissions do not wait for bb-gpu's copy (BB_SUBMIT_ASYNC=1)
out/pm4_repro/before/attack-1.log:
Submit check: 0 of 678000 graphics submissions changed before bb-gpu took them
```

`Submit check` and `BB_SUBMIT_ASYNC` do not exist at `47fa499`:

```
$ git grep -c 'Submit check' 47fa499 -- gpu        -> no match
$ git grep -l 'BB_SUBMIT_ASYNC' 47fa499            -> no match
$ git grep -l 'BB_SUBMIT_ASYNC|Submit check' 9215a10 -- gpu
9215a10:gpu/shim/remote/remote_back.cpp
9215a10:gpu/shim/remote/remote_front.cpp
```

So the `before`/`before-cold`/`delay-async` legs are 9215a10-era code (the worktree is now `1a773b6`) with
`BB_SUBMIT_ASYNC=1`, and `after` is the same build waiting. All of it is post-fix code.

| series | build | path (from the run's own log line) | runs | assert lines in the logs |
|---|---|---|---|---|
| `before` (10-17 00:29-01:02) | fix build, 9215a10-era, in `bbport-pm4-build` | `do not wait for bb-gpu's copy (BB_SUBMIT_ASYNC=1)` | 8 | 0 |
| `before-cold` | same | same, `PM4_COLD=1` (`created=217..244`) | 4 (attack-2 dead) | 0 |
| `delay-async` | same | same, `BB_SUBMIT_DELAY_US=3000` | 2 | 0 |
| `after` | same | `return once bb-gpu has copied them (BB_COPY_GPU_BUFFERS)` | 12 | 0 |
| warm-route session (10-16 16:52) | **pre-fix `77e4f46`** | copy on (see below) | 1 log of 17 survives | **1** |

## 4. The 4-of-17 is a different build, and it is the real one

The only log on this machine that contains the crash is
`~/repos/bbport-mac-native/out/warmfill/yharnam.log`, `2026-10-16 16:52`, banner `macOS run: 27.2, bbport
77e4f46`. `77e4f46` is an ancestor of `9215a10` (verified with `git merge-base --is-ancestor`), i.e. genuinely
pre-fix code. Its fatal lines:

```
Bad PM4 packet at 0x766f84ed5c: dword 0x70d1b005, 0x35c bytes into a 0x520-byte buffer at 0x766f84ea00 (IB depth 0, submission 35696; memory type -1, prot 0)
gpu critical (Debug): Unreachable code!
PM4 type 1 packet (0x70d1b005) [cp_graphics.cpp:203]
STOP: GPU library assertion failed (see GPU log above)
```

immediately after `Runtime: guest thread 'CSClothThread5' created` (line 460). This log predates the
better bad-packet report: it has no `the N packets before it` and no `the game's buffer ... differ` block,
which is what `47fa499` added. `memory type -1` at `0x766f84ea00`, inside the range printed at line 15
(`its own memory at 0x736e000000-0x796e000000`), is the doc's basis for calling the bad buffer bb-gpu's own
copy rather than guest memory; the pre-fix build prints no line naming the submit path, so that is inference
from the type, not a named config.

The 4-of-17 count itself is **not re-derivable**: only 3 logs survive in `out/warmfill/`
(`yharnam.log`, `attack.log`, `spin.log`) and exactly 1 of the 3 crashed. Three of the four crash logs are
gone - `warmfill.sh` writes `<route>.log` by name and its re-run loop overwrites. So the honest statement is:
the surviving evidence is 1 crash from that session, of the exact signature, on pre-fix code; the 4-of-17
rate rests on the session's own tally, not on disk.

## 5. Answer

- `6-of-6 asserts=1` and `0-of-8` are **the same eight runs**: post-fix code, async env, all clean. The
  `asserts=1` column is an artifact of a pre-commit loop (no `created=` column, no `summary.txt`), and the
  retained logs, which match `before.txt`'s `max_draws` exactly, contain no assertion line.
- `4-of-17` is a **different build and configuration**: pre-fix `77e4f46` on 10-16, copy on, where the crash
  is real and is the `0x70d1b005` chain at submission 35696.
- So the historical record does not contradict itself about the phenomenon. It contradicts itself about
  **which build ran**, because the "before" leg - the one meant to be the old path - was the fixed build with
  an env switch. That leg is a valid A/B of the *switch*, not of the *code*.
- Consequence for the live question: no in-game run before this session had ever put genuine pre-fix code
  under the current harness. That is what arm A does.
