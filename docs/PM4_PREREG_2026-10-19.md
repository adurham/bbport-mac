# PM4 torn-submission campaign — pre-registration (2026-10-19)

Written and committed **before the first run of the campaign**. Everything below is fixed in
advance: the arms, the sample sizes, the rule that picks D\*, what makes a run count, how a hit is
classified, and what verdict each outcome licenses. The campaign is run by
`tools/macos/pm4_repro.sh` (Phase 0) and `tools/macos/pm4_night_sweep.sh` (Phase 1); every run
appends one line to `docs/pm4-results/2026-10-19.jsonl`, and `tools/macos/pm4_analyze.py` turns
that file into the morning report. Results are read from the JSONL, not from prose.

## The question, split in two

1. **Does the fix close the tear?** That is a property of the submit/copy protocol and is provable
   tonight, synthetically, against the port's own code: `tests/test_pm4_submit.cpp`
   (`docs/PM4_SYNTHETIC_2026-10-19.md`).
2. **Is the tear what causes the `0x70d1b005` assertion?** That needs the game to cooperate: a run
   that reaches the transition after the title's Continue with a torn submission. Phase 0 asks
   whether the harness can make that happen at all; Phase 1 asks whether the fixed path is free of
   it at scale.

## Endpoint

The primary endpoint is **hash mismatch count per run**, not the assertion. `BB_SUBMIT_CHECK=1`
hashes each DCB/CCB in the game process at submit time and compares it in bb-gpu immediately before
the copy; a mismatch means the guest rewrote the buffer between the two, which is the race
regardless of whether the rewrite happens to land on a packet boundary. Asserts (`Bad PM4 packet`
/ `Unreachable code` / `GPU library assertion failed`) are recorded per run as a secondary endpoint
but are expected to be much rarer than tears.

## Phase 0 — positive control (old path only, in-game, hidden)

| arm | env | runs |
|---|---|---|
| `p0-old-d0` | `BB_SUBMIT_ASYNC=1 BB_SUBMIT_DELAY_US=0` | 3 |
| `p0-old-d500` | `BB_SUBMIT_ASYNC=1 BB_SUBMIT_DELAY_US=500` | 3 |
| `p0-old-d5000` | `BB_SUBMIT_ASYNC=1 BB_SUBMIT_DELAY_US=5000` | 3 |
| `p0-old-d50000` | `BB_SUBMIT_ASYNC=1 BB_SUBMIT_DELAY_US=50000` | 3 |

12 runs, route `attack` (every route crosses the title→area transition, which is where all three
crash dumps sit), `PM4_SECS=240`. `BB_SUBMIT_CHECK=1` is on for every run (`pm4_repro.sh` default).

**D\* selection rule.** D\* is the *smallest* `BB_SUBMIT_DELAY_US` at which **2 of 3** valid
old-path runs report at least one hash mismatch. If no delay reaches 2 of 3, D\* is undefined and
Phase 1 is not run.

**Decision after Phase 0.**
- Control positive (D\* exists): stop here, hand the parent `pm4_night_sweep.sh` with `D*`.
- Control negative (no mismatches at 50 ms): the hidden warm route does not exercise the race at a
  rate this harness can see. Phase 1 (the fixed arm) then cannot be validated in-game tonight. That
  is a finding, not a zero: it is written down as such and Phase 1 is not launched.

## Per-run validity precondition

A run counts only if its log shows **both**:

1. the title's Continue was pressed (`Runtime: pad file: buttons 0x4000`), and
2. all six area-load threads were created (`Runtime: guest thread 'CSClothThread0'` … `5`).

A run that does not reach the site is **INVALID**, not a zero. Invalid runs are excluded from the
D\* rule and reported separately by arm. (Reaching CSClothThread5 implies the transition happened;
the pad line is checked as well so a save that starts already in the area cannot pass silently.)

## Phase 1 — interleaved sweep (launched by the parent, not by this workstream)

Blocks of 4 in randomized order within each block:

| arm | env |
|---|---|
| `old` | `BB_SUBMIT_ASYNC=1` |
| `old+D*` | `BB_SUBMIT_ASYNC=1 BB_SUBMIT_DELAY_US=<D*>` |
| `fixed` | defaults (`BB_COPY_GPU_BUFFERS=1`, submit waits for the copy) |
| `fixed+D*` | `BB_SUBMIT_DELAY_US=<D*>` |

25 blocks = **100 runs**, `PM4_SECS=240`, route `attack`, appended to the same JSONL. The script
writes `SWEEPDONE <n> runs` as its last line. Blocks are interleaved so that machine load, warm-up
and any drift over the night hit all four arms alike.

## Classification of a hit (mechanical)

For every hit, the JSONL `class` field and the bad-packet report are read as follows:

| observation | class |
|---|---|
| submit hash ≠ copy hash (`Submit check: submission N … changed`) | `torn-at-copy` |
| submit hash = copy hash, and the copy-time hash ≠ the parse-time hash (`BB_PARSE_CHECK=1`) | `heap-damage-after-copy` |
| fault offset ≥ the copy's length (the bad dword is at or past `dcb_dwords`+`ccb_dwords`) | `parser-overrun` |
| submit hash = copy hash = parse-time hash, bad packet inside the buffer | `bad-in-guest` (the stream was already wrong in guest memory) |
| no hash check available for that run | `unclassified` |

`BB_PARSE_CHECK=1` (Phase 2, default off) prints, in the bad-packet report, the XXH3 of the copy
taken at copy time and the XXH3 taken immediately before the walk, so the second row is decidable
from the log alone.

## Verdict rule

| outcome | verdict |
|---|---|
| fixed arm: 0 tears, 0 asserts; old arm (or old+D\*) tears ≥ 1; Phase 0 control positive | **"fix closes the race, causality supported"** |
| fixed arm: 0 tears, 0 asserts; Phase 0 control **negative** (the harness never reproduced the race in-game) | **"fix closes the race, causality unproven in-game"** |
| fixed arm: ≥ 1 tear at the same rate as old | **"fix does not address the bug"** |
| fixed arm: fewer tears than old but the 95% interval still includes the old rate | **"unproven at this sample size"** |

Sample-size honesty: with the historical rate of ~4/17 asserts, 100 fixed-path runs with 0 asserts
bounds the assert rate at < 3% (95%, rule of three). That is not proof. The verdict sentence must
state the arm sizes and the valid-run counts; a 0-hit series is never written as "fixed".
